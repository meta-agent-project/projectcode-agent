# projectcode-tdd

코드보다 테스트를 먼저 쓴다. 테스트는 장의 코드가 실제로 돈다는 증거다.
테스트는 강의 자료에는 들어가지 않지만 저장소에는 남는다.

## 테스트 쓰는 법

- spec의 할 일 S번호마다 행동 테스트 하나를 쓴다
- 화면은 사용자가 하는 그대로 확인한다. 입력, 클릭, 보이는 글자, 이동
- API는 요청을 보내고 응답을 확인한다
- 테스트 이름은 S번호와 할 일 글로 시작한다. 예: S2 아이디와 비밀번호를 입력하면 화면이 값을 기억한다
- 화면 요소는 보이는 글자와 역할로 찾는다
- 테스트는 동작을 확인한다. 정확한 값보다 데이터가 화면으로 이어지는지를 본다. 바깥 서버 데이터에 기대지 않는다
- 테스트 때문에 학생 코드를 바꾸지 않는다. 테스트용 이름표나 내보내기를 더하지 않는다
- 테스트 도구와 실행 명령은 contract.md를 따른다
- 파일은 tests/<장>/에 둔다

## 순서

1. 읽기
   이 장의 spec.md, plan.md, contract.md를 읽는다.

2. 테스트 쓰기
   위 쓰는 법대로 쓴다.
   리팩터 장은 동작이 바뀌지 않으므로 새 테스트 없이 지금 테스트가 모두 통과하는지만 확인한다.
   할 일이 확인할 수 있는 동작이면 그 할 일만 테스트를 쓴다.

3. 앞 장 테스트 고치기
   이 장이 앞 장의 동작을 바꾸면 그 장의 테스트를 지금 동작에 맞게 고친다.
   예: 콘솔에 보여주던 가입하기가 이 장에서 서버 요청으로 바뀐다
   이 커밋에 Touches: <그 장>을 붙인다.
   - 문서는 그 장 시점의 스냅샷이라 고치지 않는다. 테스트는 코드라서 지금 동작을 따른다
   - 장별 코드를 뺄 때 Touches 커밋이 빠지므로, 앞 장 시점 코드에는 앞 장 시점 테스트가 남는다

4. 실패 확인
   이 장의 테스트를 실행한다. 모두 기능이 없어서 실패해야 한다.
   - 이미 통과하는 테스트는 의미가 없으니 고친다
   - 문법이나 불러오기 오류로 실패하면 테스트를 고친다

5. 커밋
   tasks.md의 테스트 작성을 체크하고 함께 커밋한다.
   제목: [장] 테스트 작성
   본문: Chapter, Kind: test, 필요하면 Touches
   이 커밋이 테스트 잠금이다. implement는 이 커밋 뒤로 테스트 파일을 바꾸지 않는다.

6. 다음
   projectcode-implement라고 알린다.

## project-setup 장일 때

테스트 도구가 아직 없다. 테스트 파일만 쓰고 커밋한다.
실패 확인은 implement가 테스트 도구를 설치한 task 뒤에 한다.

## 예시

```
test("S2 아이디와 비밀번호를 입력하면 화면이 값을 기억한다", async ({ page }) => {
  await page.goto("/")
  await page.getByLabel("아이디").fill("kim")
  await expect(page.getByLabel("아이디")).toHaveValue("kim")
})
```
